# Fix notification_attempts id type + atomic dedup guard

## Problem

Two independent, small bugs in the notification-persistence path:

1. **`notification_attempts.id` is declared `UUID`** in `V1.0.0__Init_Schema.sql`,
   but `NotificationAttempt extends PanacheEntity`, whose `id` field is
   `Long` with `@GeneratedValue`. The Flyway-defined schema and the JPA mapping
   disagree.
2. **`NotificationService.persistRecord()` dedups via check-then-act**:
   `findById(id) != null → return`, else `persist()`. Not atomic — two
   concurrent calls with the same id can both pass the check, and the loser's
   `persist()` throws an unhandled exception instead of a clean response.

### A third bug found during investigation, folded into item 1

Flyway's default migration location is `classpath:db/migration` (singular).
This repo's migrations live in `db/migrations` (plural), and no property
anywhere overrides `quarkus.flyway.locations`. Confirmed empirically (ran a
`@QuarkusTest` against Testcontainers Postgres with SQL logging): Flyway logs
`"No migrations found"` and applies zero migrations, in every profile. The
schema that actually exists everywhere — dev, test, and per user confirmation
prod — is generated entirely by
`quarkus.hibernate-orm.schema-management.strategy=update`, i.e. Hibernate's
own auto-DDL from the `@Entity` mappings.

Consequence, also confirmed empirically (native query against
`information_schema` inside a `@QuarkusTest`): `notification_attempts.id` is
**already `bigint`** in every real environment, backed by an
auto-created sequence `notification_attempts_seq`, with no column-level
`DEFAULT` (Hibernate calls `nextval()` explicitly before each insert and
passes the value — it never relies on a DB default). `V1.0.0`'s `UUID`
declaration has never actually been applied anywhere; it only exists on paper.

This means the id-type migration must be written defensively: it has to leave
a real prod database (already `bigint`, Hibernate-managed) alone, while also
correctly converting a fresh database (where, once the location bug is fixed,
`V1.0.0` really will run for the first time and really will create a `UUID`
column) to the same end state. Both branches are exercised by the plan below.

## Goal / Non-goals

Goals:
- `notification_attempts.id` is `BIGINT`, generated by a correctly-wired
  Postgres sequence, on every database this app touches — expressed
  explicitly in a Flyway migration, not left to Hibernate auto-DDL.
- Flyway migrations actually apply from this point forward (locations fixed),
  without re-running `V1.0.0`–`V1.0.2` as real DDL against databases that
  already have that shape (via `baseline-on-migrate` + an explicit
  `baseline-version`).
- `NotificationService.persistRecord()`'s duplicate-id case is handled
  atomically: a real DB constraint violation, caught and turned into a 409,
  not a check-then-act race.

Non-goals:
- Turning off `quarkus.hibernate-orm.schema-management.strategy=update`.
  Two schema authorities (Flyway + Hibernate auto-DDL) coexisting is a
  pre-existing architectural smell (the `# could be redundant` comment
  already next to it agrees), but disabling it is a bigger, separately-risky
  change that deserves its own mission and broader testing, not a rider on
  this one. Flagged below under Risks.
- Rewriting `DeduplicationService`'s Redis-based intake dedup (recipient +
  channel + content hash, TTL-based). Untouched — see Design for why it's a
  different mechanism from the one this mission fixes.
- Any change to `NotificationRecord`/`notifications` schema. The dedup fix
  needs no new column or constraint — see Design.

## Design

### 1. Flyway location + baseline (prerequisite, not its own migration)

`application.properties`:
```
quarkus.flyway.locations=classpath:db/migrations
quarkus.flyway.baseline-version=1.0.2
```
`baseline-on-migrate=true` is already set. With an explicit baseline version,
Flyway on a non-empty schema with no `flyway_schema_history` table (every
real deployment today) baselines at `1.0.2` and applies only migrations
numbered above it — `V1.0.0`–`V1.0.2` are recorded as already-done, never
re-executed as DDL. On an empty schema (every fresh Testcontainers test run),
baselining doesn't trigger; Flyway runs `V1.0.0` onward for real, which is
exactly what lets us integration-test the real UUID→BIGINT conversion.

### 2. `V1.0.3__Fix_notification_attempts_id_type.sql`

**Existing rows / FK impact:** `notification_attempts` is a pure,
append-only audit trail (`NotificationStateService.updateStatus()` /
`recordAttemptFailure()` — write-only, never read back by id, never returned
by any API: `FailedNotificationResponse` only exposes fields from
`NotificationRecord`). The only foreign key touching this table is
`notification_attempts.notification_id REFERENCES notifications(id)` — it
points at `notifications.id` (untouched by this migration) and is unaffected
either direction. Nothing references `notification_attempts.id` from
anywhere.

**Decision: treat as resettable, do not preserve old id values.** No
consumer, in code or over the API, cares what an attempt row's id *is* —
only that each row has *some* unique id and that new ones keep generating
correctly. So the migration does not attempt to map old UUID values to new
Long values; where an old UUID column exists, it's simply dropped after the
new BIGINT column is populated with fresh sequence values. This means a
single migration is sufficient — no expand/contract needed, because
expand-contract exists to protect readers who depend on the old shape during
a rolling deploy, and there are none here.

**No window without a PK:** the migration runs as one Flyway-managed
transaction (Postgres DDL is transactional); the old PK constraint is only
ever dropped and the new one added within that same transaction.

**Identity/sequence wiring**, using `information_schema` checks so the
migration is correct against both realities described above:
- If `id` is currently `uuid`: drop the PK, drop the old column, add a new
  `BIGINT` column.
- `CREATE SEQUENCE IF NOT EXISTS notification_attempts_seq` (matches the
  name Hibernate's default `GenerationType.AUTO` already picked, confirmed
  empirically — reusing it rather than inventing a different name means
  Hibernate's schema-management=update pass, which still runs after Flyway,
  sees no drift and does nothing).
- Backfill any null ids from the sequence, set `NOT NULL`, set
  `DEFAULT nextval(...)` (belt-and-suspenders; Panache doesn't rely on it but
  it protects any future non-Hibernate writer), `ALTER SEQUENCE ... OWNED BY`
  for correct lifecycle/cleanup semantics, advance the sequence past
  `MAX(id)`, and (re)add the `PRIMARY KEY` if not already present.
- Every step is `IF EXISTS`/`IF NOT EXISTS`/conditional, so re-running it
  against an already-correct (Hibernate-built) prod schema is a safe no-op.

### 3. Dedup guard — `NotificationService.persistRecord()`

**Natural key: `notifications.id`.** It's already the table's `PRIMARY KEY`
(`V1.0.0`: `id VARCHAR(255) NOT NULL PRIMARY KEY`) — a real, already-enforced
unique constraint. No new migration is needed for this item; the bug is
purely in the application code racing around a constraint that already
exists.

Investigated how `id` is actually populated: `NotificationMapper.toDomain()`
mints a fresh `UUID.randomUUID().toString()` for every incoming request —
`request.getId()` is never client-supplied and never reused by any other
caller (`dispatchNotification()`/`persistRecord()` has exactly one call site,
`NotificationResource`). So today, two calls can never legitimately collide,
which is *why* this bug hasn't surfaced as an incident. The check-then-act
pattern is still wrong: it's dead code offering false protection, and if a
genuine id collision ever occurs (retried request, future idempotency-key
support), the loser's bare `persist()` throws an unhandled
`ConstraintViolationException` → 500, instead of a clean response.

**Fix:** delete the `findById` pre-check. Call `persist()` then an explicit
`flush()` (forces the `INSERT` — and thus the constraint check — to happen
synchronously inside the method, before the `REQUIRES_NEW` transaction
commits; without it Hibernate may defer the insert to commit time, after the
catch block has already been exited). Catch
`org.hibernate.exception.ConstraintViolationException` and translate it to a
new `DuplicateNotificationException` (subclass of the existing
`NotificationException`, reusing the existing generic
`NotificationExceptionHandler` mapper — no new mapper needed), mapped to
**409** via a new `NotificationErrorCode.DUPLICATE_NOTIFICATION` /
`ErrorCategory.CONFLICT`, following the exact pattern `RateLimitException`
already established. New i18n keys added to both
`messages_en.yaml`/`messages_bg.yaml`, matching the existing key-naming
scheme.

**Why not touch `DeduplicationService`:** that's a different, deliberately
separate guard — Redis, TTL-scoped (5m default), keyed on
recipient+channel+content-hash, fail-open by design, checked once at intake
to catch duplicate *requests*. A permanent DB unique constraint on that same
content-based key would be actively wrong (it would forbid ever legitimately
re-sending the same templated message to the same recipient after the TTL
expires). The bug in scope here is narrower and different in kind: an
already-unique column (`id`) guarded with a racy check instead of relying on
the constraint that already backs it.

## Risks & open questions

- **Two schema authorities remain.** Flyway becomes real again, but
  Hibernate's `schema-management.strategy=update` still runs after it on
  every boot. As long as the two agree (which this migration is written to
  guarantee for `notification_attempts`), this is a no-op overlap, not a
  conflict — but it's fragile long-term and worth a dedicated follow-up
  mission to pick one authority. Not addressed here (see Non-goals).
- **Unverified assumption:** prod's real schema state was confirmed by you,
  not by direct inspection of the production database (I have no access to
  it). The migration is written defensively (idempotent, branches on actual
  column type) specifically so it's still correct even if that assumption
  turns out to be wrong for some environment.
